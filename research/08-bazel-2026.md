## 2. Release timeline & LTS policy

### 2.1 Policy (https://bazel.build/release, fetched 2026-08-25)

- Two tracks: **rolling** (cut from HEAD ~every 2 weeks, coordinated with Google's
  internal Blaze release; may ship incompatible changes) and **LTS** (major cut from
  HEAD ~every 12 months).
- Support stages: Rolling → Active → Maintenance → Deprecated. An LTS goes Deprecated
  after 2 years in Maintenance.
- Minor releases on the Active LTS every ~2 months; patches on demand.

## 3. WORKSPACE removal — verified exactly

### Timeline

| Version | State |
|---|---|
| Bazel 6 (2022-12) | Bzlmod GA but off by default |
| Bazel 7 (2023-12) | `--enable_bzlmod` defaults **true**; WORKSPACE still read |
| Bazel 8 (2024-12) | `--enable_workspace` defaults **false**; WORKSPACE/`WORKSPACE.bzlmod` no longer read unless you pass `--enable_workspace` |
| **Bazel 9 (2026-01-20)** | **all WORKSPACE code deleted**; both flags are no-ops |

Bazel 8.7.0's own command-line reference (`docs/versions/8.7.0/reference/command-line-reference.mdx`):
```
--[no]enable_bzlmod    default: "true"
--[no]enable_workspace default: "false"
    If true, enables the legacy WORKSPACE system for external dependencies.
```

At HEAD (`src/main/java/com/google/devtools/build/lib/bazel/rules/BazelRulesModule.java:1417`):
```java
@Deprecated
@Option(
    name = "enable_workspace",
    defaultValue = "false",
    documentationCategory = OptionDocumentationCategory.UNDOCUMENTED,
    effectTags = OptionEffectTag.LOADING_AND_ANALYSIS,
    metadataTags = {OptionMetadataTag.DEPRECATED},
    help = "No-op.")
public abstract boolean getEnableWorkspace();
```
Same for `enable_bzlmod` (line ~1407). Bazel 9.0.0 release notes: *"Bzlmod is now always
enabled, and all `WORKSPACE` logic has been removed from Bazel
([#26131](https://github.com/bazelbuild/bazel/issues/26131))… The `--enable_bzlmod` and
`--enable_workspace` flags are now no-ops."*

Related removals in 9.0: `bazel sync` removed (use `bazel fetch --all`);
`--incompatible_disable_native_repo_rules` flipped;
`@bazel_tools//tools/build_defs/repo:maven_rules.bzl` deleted.

### What still references WORKSPACE at HEAD

`WORKSPACE` and `WORKSPACE.bazel` are **still repo-boundary marker filenames**:
`LabelConstants.java:37-38` still defines `WORKSPACE_FILE_NAME` /
`WORKSPACE_DOT_BAZEL_FILE_NAME`, used by `RepositoryUtils.java:47`,
`PathPackageLocator.java:269`, `RBuildFilesVisitor.java:288`. So a directory containing
only a `WORKSPACE` file is still recognised as a repo root; its *contents* are simply
never evaluated. `bazel.build/external/overview` documents this: a repo boundary marker
may be `MODULE.bazel`, `REPO.bazel`, "or in legacy contexts, `WORKSPACE` or
`WORKSPACE.bazel`".

`PackageFunction.java:385` still emits a dedicated error for `//external`:
> `"//external package is not available since the WORKSPACE file is deprecated, please migrate to Bzlmod."`

### How much of the ecosystem has migrated

Two hard data points, both awkward for the "it's done" narrative:

1. **~60% Bzlmod adoption** — Bazel's own user survey (Feb 2025). Quoted by maintainer
   `meteorcloudy` in [discussion #27142](https://github.com/bazelbuild/bazel/discussions/27142)
   (2025-10-06) and confirmed by the Dependabot team ("the ~60% Bzlmod adoption from the
   survey is encouraging"). *No 2026 survey has been run* — the last one is
   [#25659](https://github.com/bazelbuild/bazel/discussions/25659) (results 2025-03-21).
2. **GitHub code search, July 2025** (Alan Mond,
   https://alanmond.com/posts/bazel-documentation-improvements/): `path:WORKSPACE AND
   language:Starlark` → **47,900** files; `path:MODULE.bazel AND language:Starlark` →
   **12,200**. ≈ 80% / 20%. (Noisy — a repo can have both, and stale/abandoned repos
   dominate open-source corpora — but the direction is unambiguous.)

The Bazel 9 blog post itself concedes: *"But we know the work isn't over; migration is
hard, and **many users are still on the old WORKSPACE system**."*

**LSP implication.** WORKSPACE parsing is not optional and will not be optional for
years. Concretely:
- Bazel 7 is supported until **Dec 2026** and reads WORKSPACE by default.
- The official migration tool **only runs on Bazel 7** (`bazel.build/external/migration_tool`:
  "Use the migration tool with Bazel 7 (not supported with Bazel 8)"), so every repo that
  hasn't migrated has to route through a version that goes EOL in four months.
- A large share of public repos still have a WORKSPACE. An LSP that refuses to open them
  is useless to exactly the population that most needs tooling help.
- Cheap upside: `WORKSPACE`/`WORKSPACE.bazel`/`WORKSPACE.bzlmod` are ordinary Starlark
  with a known global set (`workspace()`, `register_toolchains()`,
  `register_execution_platforms()`, `bind()`, repo rules). Treat it as a fourth dialect
  alongside BUILD / .bzl / MODULE.bazel, not as a first-class resolution source.

## 4. Symbolic macros

### 4.1 What they are

Introduced in Bazel 8.0 (2024-12-09), **on by default**
(`--experimental_enable_first_class_macros` default `"true"`,
`BuildLanguageOptions.java`). Design discussion:
[bazelbuild/bazel#19921](https://github.com/bazelbuild/bazel/discussions/19921)
(brandjon, 2023-10-23; "Status update, Oct 2024: This is implemented and will be
released with Bazel 8.0"); the 2-page design doc it links to is a Google Doc
(`docs.google.com/document/d/1aOp2TsS6iM0byBxrGMKgnUnBR2ihYr2RGeYuScvduUg`).
Tracking issue for follow-ups: **#19922**.

Implementation:
- `src/main/java/com/google/devtools/build/lib/packages/MacroClass.java` (556 lines) —
  "analogous to `RuleClass`. In essence, a `MacroClass` consists of the macro's schema
  and its implementation function."
- `MacroInstance.java` (404 lines), `RuleOrMacroInstance.java`
- Starlark API surface: `StarlarkRuleFunctionsApi.java` (`macro(...)`),
  `StarlarkRuleClassFunctions.java`
- `starlarkdocextract/ModuleInfoExtractor.java` — Stardoc understands them

```starlark
my_macro = macro(
    implementation = _impl,     # must take at least `name` and `visibility`
    attrs = {...},              # attr.* objects, or None to *delete* an inherited attr
    inherit_attrs = None,       # rule symbol | macro symbol | "common" | None
    finalizer = False,
    doc = None,
)
```

### 4.2 The tooling/IDE rationale — say it explicitly

This is the part that matters for us. Legacy macros are arbitrary Python-ish functions;
after the loading phase they have evaporated and Bazel retains almost nothing about
them. `bazel.build/extending/concepts`:

> "The function is evaluated as soon as the `BUILD` file is read. **After the evaluation
> of the `BUILD` file, Bazel has little information about macros.**"

Symbolic macros exist to make that information survive. Three of the design's four
pillars are directly static-analysis properties:

1. **Typed attribute schema.** A `macro()` has an attribute schema exactly like a rule,
   introspectable without running it. This is what makes completion of macro call
   arguments, hover docs on attributes, and "unknown attribute" diagnostics possible for
   macro calls — impossible for a legacy `def`.
2. **The naming rule makes target ownership statically decidable.**
   `StarlarkRuleFunctionsApi.java`, `macro.implementation` doc:
   > "The name of any target or inner symbolic macro declared by a symbolic macro
   > (including by any Starlark function that the macro's implementation function
   > transitively calls) must either equal `name` (this is referred to as the 'main'
   > target) or start with `name`, followed by a separator character (`"_"`, `"-"`, or
   > `"."`) and a string suffix. (Targets violating this naming scheme are allowed to be
   > declared, but cannot be built, configured, or depended upon.)"

   The docs are explicit that this exists to let Bazel *avoid* evaluating the macro:
   > "The prefix naming schema helps Bazel determine which macro to expand given a
   > requested target." (`site/en/extending/macros.md:434`)

   That is *exactly* the goto-definition problem: given `//pkg:foo_bar`, which
   declaration site produced it? With a legacy macro you must interpret arbitrary
   Starlark; with a symbolic macro it is a string-prefix lookup.
3. **Purity restrictions.** The commit that landed them
   ([d4f30a6](https://github.com/bazelbuild/bazel/commit/d4f30a671787b8b96824c05df9ba037782cd7f4f))
   says:
   > "Symbolic macros are not permitted to call APIs that depend upon the order in which
   > they are invoked relative to the rest of the package's evaluation… **This
   > restriction is to enable future lazy evaluation of symbolic macros**, as well as
   > general build health."

   Banned inside a symbolic macro: `package()`, `licenses()`, `environment_group()`,
   `glob()`, `subpackages()`, `existing_rule()`, `existing_rules()` (finalizers
   excepted), plus all repo machinery (`workspace()`, `register_toolchains()`,
   `register_execution_platforms()`, `bind()`, repo rule instantiation).

   `glob()` in particular being banned is a gift: a symbolic macro's target set does not
   depend on the filesystem.
4. **Macro-aware visibility** — see 4.4.

### 4.3 Lazy evaluation is IMPLEMENTED at HEAD (the docs say it isn't)

`bazel.build/extending/macros` and `docs/extending/macros.mdx:424-427` still say:

> "**IMPORTANT: We are in the process of implementing lazy macro expansion and
> evaluation. This feature is not available yet.**"

But at HEAD it exists, per-package opt-in:

```java
// src/main/java/com/google/devtools/build/lib/pkgcache/PackageOptions.java:222
@Option(
    name = "experimental_lazy_macro_expansion_packages",
    defaultValue = "",
    converter = LazyMacroExpansionPackages.OptionConverter.class,
    documentationCategory = OptionDocumentationCategory.UNDOCUMENTED,
    effectTags = {LOADING_AND_ANALYSIS, LOSES_INCREMENTAL_STATE},
    metadataTags = {EXPERIMENTAL},
    help = "List of packages in which symbolic macro are expanded only if necessary.")
```

with real machinery behind it — a whole new "package piece" layer:
`packages/PackagePiece.java`, `packages/PackagePieceIdentifier.java`,
`packages/NoSuchPackagePieceException.java`, `skyframe/PackagePieceValue.java`,
`skyframe/PackagePieces.java`, `skyframe/NonFinalizerPackagePiecesFunction.java`, and
`PackageFunction#computePackageFromPackagePieces` (`PackageFunction.java:391`).

**This is the single most LSP-relevant thing in the Bazel 9/10 codebase.** It means
Bazel itself now has an internal API shaped like "resolve one target without loading the
whole package", which is precisely the query an LSP wants for goto-definition and hover
in a 5,000-target BUILD file.

### 4.4 Visibility semantics (macro-aware visibility)

From `docs/extending/macros.mdx` §Visibility and macros:

1. "Visibility is checked based on **what macro declared the target**, not what package
   called the macro." Being in the same package no longer implies mutual visibility.
2. "All `visibility` attributes, on both rules and macros, **automatically include the
   place where the rule or macro was called**."
3. Default: a target declared in a macro without an explicit `visibility` is **internal
   to the macro**. The package's `default_visibility` does **not** apply inside a macro.
4. To export, forward: `some_rule(..., visibility = visibility)`.

`MacroClass.java:76`:
```java
public static final Attribute VISIBILITY_ATTRIBUTE =
    Attribute.attr("visibility", NODEP_LABEL_LIST)
        .orderIndependent()
        .nonconfigurable("special attribute integrated more deeply into Bazel's core logic")
        .build();
```
`RESERVED_MACRO_ATTR_NAMES = {"name", "visibility"}` (`MacroClass.java:69`) — `name` is a
real attribute, `visibility` is reserved and injected.

**LSP implication**: "is `//a:b` visible from `//c:d`?" is no longer a package-level
question. A visibility diagnostic must know the declaring macro instance, not just the
declaring package. Bazel added `--verbose_visibility_errors` in 9.0 for this reason.

### 4.5 `inherit_attrs`

Added in Bazel 9.0 ("Added `inherit_attrs` param to `macro()`"). Rules, verbatim from
`StarlarkRuleFunctionsApi.java`:

1. `name` and `visibility` are never inherited.
2. Hidden attributes (`_`-prefixed) are never inherited.
3. Names already in `attrs` are never inherited (`attrs` wins; set to `None` to *delete*).
4. Everything else is merged in.
5. **"When a non-mandatory attribute is inherited, the default value of the attribute is
   overridden to be `None`"** — so the macro can distinguish "not passed" from "passed
   the default". Implementations must handle `None`.
6. `inherit_attrs` requires the impl function to have `**kwargs`.
7. `inherit_attrs = "common"` inherits the standard common rule attributes.
8. Only works on symbols that were assigned to a **global variable** in a `.bzl` file
   ("if the return value of `rule()` or `macro()` was not assigned to a global variable
   … it has not been registered as a rule or macro symbol").

**LSP implication**: to complete attributes on `my_cc_library(...)` you must resolve
`inherit_attrs = native.cc_library` — which in Bazel 9 means resolving into
`@rules_cc`, running its `.bzl`, and reading *its* attribute schema. Attribute
completion is now a cross-repo transitive problem.

### 4.6 `finalizer = True`

Rule finalizers run at the end of package loading regardless of position in the BUILD
file, and are the *only* symbolic macros allowed to call `native.existing_rule()` /
`native.existing_rules()` — and those only see **non-finalizer** targets. Lazy expansion
does not apply to finalizers (hence `NonFinalizerPackagePiecesFunction`).

### 4.7 Strictness flag

`--incompatible_symbolic_macro_strict_attrs` (default `false` at HEAD,
`BuildLanguageOptions.java:616`): "If enabled, invalid attribute values in symbolic
macros are treated as an error and fail the build" (matching rule behaviour). Landed in
rolling `10.0.0-pre.20260723.1`. Not yet flipped.

### 4.8 Adoption

Migration is live but early. Evidence:
- Tweag, "Migrating to Bazel symbolic macros", 2025-11-20
  (https://www.tweag.io/blog/2025-11-20-migrating-bazel-symbolic-macros/), HN 24 points
  2025-11-22.
- Bazel's own repo contains **zero** `= macro(` definitions in `tools/` or `src/`
  (grepped at HEAD). The core project has not eaten its own dogfood.
- Legacy macros still have a full doc page (`/extending/legacy-macros`) and a tutorial
  (`/rules/legacy-macro-tutorial`), and Bazel's own guidance is hedged: "Where possible,
  we recommend using symbolic macros for code clarity."

**Practical conclusion for the LSP: legacy `def`-based macros will be the dominant form
in real repos for the foreseeable future.** Symbolic macros are the tractable case;
design for the intractable one and treat symbolic macros as the fast path.

## 5. Other language-visible Bazel 8/9/10-pre changes

### 5.1 Starlark type annotations — already parseable, today

**This is a syntax change to Starlark and it is already live in Bazel 9.**

Bazel 9.0.0 release notes, Starlark section:
> "OSS Bazel **permits but ignores type annotations in `.bzl` files**. Type annotations
> are experimental, and code that uses them may fail in future versions of Bazel."

Flag defaults (from the in-repo versioned command-line references):

| flag | 8.7.0 | 9.0.0 | 9.1.0 | HEAD |
|---|---|---|---|---|
| `--experimental_starlark_type_syntax` | *absent* | **true** | **true** | **true** |
| `--experimental_starlark_types_allowed_paths` | — | `""` (= all) | `""` | `""` |
| `--experimental_starlark_static_type_checking` | — | false | false | false |
| `--experimental_starlark_dynamic_type_checking` | — | false | false | false |

`packages/semantics/FlagConstants.java`:
```java
// Enable annotations, but not actual type checking, with the effect that the parser
// tolerates arbitrary expressions in annotations for now.
public static final String EXPERIMENTAL_STARLARK_TYPE_SYNTAX_FLAG_NAME =
    "+experimental_starlark_type_syntax";
public static final String DEFAULT_EXPERIMENTAL_STARLARK_TYPE_SYNTAX = "true";
```

New AST node types in `src/main/java/net/starlark/java/syntax/` that a Starlark parser
must now handle:

| File | Syntax | `Node.Kind` |
|---|---|---|
| `VarStatement.java` | `foo : int` (bare annotation, no initialiser) | `VAR` |
| `TypeAliasStatement.java` | `type Foo = ...`, with type parameters | `TYPE_ALIAS` |
| `TypeApplication.java` | `list[str]`, `dict[str, int]` | `TYPE_APPLICATION` |
| `CastExpression.java` | `cast(T, v)` | `CAST` |
| `IsInstanceExpression.java` | `isinstance(v, T)` | `ISINSTANCE` |
| `Ellipsis.java` | `...` | `ELLIPSIS` |
| `DocComments.java` | Sphinx-autodoc-style `#:` / `#: text` doc comments | — |

Supporting: `StarlarkType.java`, `TypeChecker.java`, `TypeConstructor.java`,
`TypeContext.java`, `TypeTable.java`, `TypeTagger.java`, `Types.java`.
`Parser.java:97`: *"`type` is a keyword iff it precedes an identifier (such as in a type
alias expression)"* — a soft keyword, which is a real parser complication.
`Parser.java:567`: `isinstance_expression = 'isinstance' '(' expr ',' TypeExpr [','] ')'`.

`FileOptions` gained `allowTypeSyntax`, `resolveTypeSyntax`,
`tolerateInvalidTypeExpressions` (`BzlCompileFunction.java:283-291`).

Not permitted: in `.scl` files, in the BUILD prelude, in `@_builtins`, in
`@bazel_tools` (`BzlCompileFunction.java:249-258`).

**LSP implications, in order of urgency:**
- Any grammar we adopt (`tree-sitter-starlark`, `starlark-rust`, hand-rolled) **must
  already accept these forms or it will report false syntax errors on Bazel 9 repos
  today.** Check every candidate parser against `x: int = 1`, `def f(a: str) -> None:`,
  `type Foo = list[str]`, `isinstance(x, int)`, `cast(int, x)`, `...`.
- Once typing ships in Bazel 10, `#:` doc comments and annotations become the primary
  source for hover text and signature help — better than today's stringly-typed
  `doc = "..."`.
- Related open issue for us:
  [#21979](https://github.com/bazelbuild/bazel/issues/21979) "Stardoc protos and
  `ModuleInfoExtractor` / `starlark_doc_extract` should export parameter type
  annotations" (13 reactions, updated 2026-02-28).

### 5.2 `.scl` — the Starlark Configuration Language dialect

**A genuinely new file type, on by default, and *completely undocumented in prose*.**

- `--experimental_enable_scl_dialect` default **`"true"`** in 8.7.0, 9.0.0, 9.1.0 and
  HEAD.
- `.scl` is a *restricted* Starlark dialect, handled by the same
  `BzlCompileFunction`/`BzlLoadFunction` machinery as `.bzl`
  (`BzlLoadValue.java:45-49`: "assume any 'bzl' term could mean a `.scl` file as well").

Restrictions, from `BzlLoadFunction.java` and `BzlCompileFunction.java`:

| Restriction | Source |
|---|---|
| `.scl` may only `load()` other `.scl`, never `.bzl` | `BzlLoadFunction.java:1009-1012` |
| load labels must begin with `//` — **no `@repo` syntax, no relative labels** | `BzlLoadFunction.java:1092` |
| string literals must be **ASCII-only** | `BzlCompileFunction.java:201`, `.stringLiteralsAreAsciiOnly(key.isSclDialect())` |
| type annotations forbidden | `BzlCompileFunction.java:252`, "not yet compatible with Go-Starlark interpreter" |
| no builtins injection | `BzlLoadFunction.java:1360` |

The **entire predeclared environment of a `.scl` file is two symbols**
(`analysis/starlark/StarlarkGlobalsImpl.java:111-126`):
```java
public ImmutableMap<String, Object> getSclToplevels() {
  ...
  env.put("visibility", visibilitySymbol);
  env.put("struct", StructProvider.STRUCT);
  return env.buildOrThrow();
}
```
Plus one magic label: `//:project_proto.scl` is rewritten to
`@bazel_tools//src/main/protobuf/project:project_proto.scl` because `.scl` cannot
express `@repo` (`BzlLoadFunction.java:1094-1098`).

### 5.3 `PROJECT.scl` (project files / "Flagsets")

`skyframe/ProjectFilesLookupFunction.java:35`:
```java
@VisibleForTesting public static final String PROJECT_FILE_NAME = "PROJECT.scl";
```

- Discovered by walking **up** the directory tree from the target's package; **only the
  innermost matching file applies** (`Project.java:118`, `ProjectFilesLookupValue.java:46`).
- Must define exactly one top-level variable named `project`
  (`ProjectFunction.java:43-61`): *"Project files must define exactly one top-level
  variable called `project`"*.
- Two schemas coexist: a legacy `dict` form (`parseLegacyProjectSchema`) and the current
  proto-backed struct form (`parseProtoProjectSchema`), the latter built from
  `src/main/protobuf/project/project_proto.scl` (generated by "Protolark") exposing
  `project_pb2.Project.create(name, buildable_units, enforcement_policy,
  project_directories, always_allowed_configs)`, `buildable_unit_pb2.BuildableUnit.create(
  name, target_patterns, flags, description, is_default)` and
  `enforcement_policy_pb2.EnforcementPolicy` ∈ {`UNSPECIFIED`, `WARN`, `COMPATIBLE`, `STRICT`}.
- Supports **aliasing**: `{"actual": "//other:PROJECT.scl"}` delegates
  (`ProjectValue.java:147-152`).
- Selected with `--scl_config=<name>` (`CoreOptions.java:80`, UNDOCUMENTED, EXPERIMENTAL,
  "Note that this feature is still under development b/324119879").
- Flags from a `PROJECT.scl` are deliberately not counted as "explicit"
  (`ParsedOptionDescription.java:204`).
- Also feeds flag *scoping* (`config/Scope.java:39,77`,
  `BuildOptionsScopeFunction.java`) and remote analysis caching
  (`RemoteAnalysisCacheFactory.java:297`).

Community coverage: "Managing Bazel Flags in Monorepos with Flagsets (PROJECT.scl)" by
Adin Ćebić (linked in the Q1 2026 community update); BazelCon 2025 talk **"Flagsets" —
Susan Steinman & Greg Estren, Google** (2025-11-11, general session slot). Tracking issue
[#24839](https://github.com/bazelbuild/bazel/issues/24839) (P1, `team-Configurability`,
18 reactions).

**LSP implication**: `*.scl` and `PROJECT.scl` are new first-class file types. They are
cheap to support well because the language surface is tiny (two globals) and the
`PROJECT.scl` schema is a fixed, known proto. Nobody else supports them. There is
literally no prose documentation to compete with — see §7.

### 5.4 Autoloading of native rules — gone

- Bazel 8.0: `--incompatible_autoload_externally` introduced with a large non-empty
  default. 8.7.0's reference shows it verbatim:
  ```
  default: "+@rules_python,+java_common,+JavaInfo,+JavaPluginInfo,ProguardSpecProvider,
  java_binary,java_import,java_library,java_plugin,java_test,java_runtime,java_toolchain,
  java_package_configuration,@com_google_protobuf,@rules_shell,+@rules_android"
  ```
  Semantics: `+foo` = autoload `foo` except in its own repo; `foo` = autoload and hide
  the Bazel version from excluded repos; `-foo` = don't autoload and make the Bazel
  version inaccessible.
- Bazel 9.0: default flipped to `""`; `--incompatible_disable_autoloads_in_main_repo`
  flipped to true. C++ rules moved to `rules_cc`. "This marks the conclusion of the
  Starlarkification effort."
- HEAD: flag is a `@Deprecated` NO_OP; `AutoloadSymbols` no longer exists in the tree.

**LSP implication**: in Bazel 9+, **no** language rule is implicitly available.
`cc_library`, `java_library`, `py_binary`, `sh_test`, `proto_library` all require an
explicit `load()` from `@rules_cc` / `@rules_java` / `@rules_python` / `@rules_shell` /
`@protobuf`. That makes:
- "missing `load()`" the single highest-value diagnostic, and the corresponding
  quick-fix ("add `load("@rules_cc//cc:cc_library.bzl", "cc_library")`") the single
  highest-value code action. Bazel's own migration advice for this is literally
  `buildifier --lint=fix -r ./`
  ([discussion #28344](https://github.com/bazelbuild/bazel/discussions/28344)).
- the set of "builtin" symbols version-dependent: a 7.x repo has ~40 implicit rule
  names, a 9.x repo has ~0. The LSP must key its builtin table on the repo's Bazel
  version (`.bazelversion` / `bazelisk`).

### 5.5 Bzlmod file types and syntax an LSP must know

`MODULE.bazel` globals (`bazel/bzlmod/ModuleFileGlobals.java`): `module`, `bazel_dep`,
`register_execution_platforms`, `register_toolchains`, `use_extension`, `use_repo`,
`override_repo`, `inject_repo`, `use_repo_rule`, `include`, `single_version_override`,
`multiple_version_override`, `archive_override`, `git_override`, `local_path_override`.

- **`include()` introduces a new filename convention.** From the API doc:
  > "The label must point to a file in the main repo; in other words, it **must** start
  > with double slashes (`//`). The name of the file must end with **`.MODULE.bazel`**
  > and must not start with `.`."
  >
  > "variable bindings (such as those used for `use_extension`) are only ever visible in
  > the file they occur in, not in any included or including files."

  So `*.MODULE.bazel` segment files are a real file type, with *file-local* binding
  scope — a subtle rule for goto-definition on `use_extension` proxies.
- **Canonical repo names use `+`, not `~`** (changed in Bazel 7.4/8). `ModuleKey.java:97-127`:
  ```java
  // This results in canonical repository names such as `rules_foo+` for the module `rules_foo`.
  ...
  return RepositoryName.createUnvalidated(String.format("%s+%s", name, suffix));
  ```
  With version: `rules_foo+1.2.3`. Module extension repos:
  `ModuleExtensionId.java:68` → `module() + "+" + usageExportedName()`, e.g.
  `rules_foo+1.2.3+ext+repo`. Root module canonical name is the **empty string**;
  `@@//pkg:t` addresses the main repo. Well-known modules (`bazel_tools`, `platforms`,
  `local_config_platform`) keep bare names.
- **Bazel 9 changed `use_repo_rule` canonical names**: *"The canonical names of repos
  created with `use_repo_rule` have changed to be more stable."* Any LSP that caches
  canonical names across versions will be wrong.
- `bazel mod` subcommands (`bzlmod/modcommand/ModOptions.java:232`): `deps`, `graph`,
  `all_paths`, `path`, `explain`, `show_repo`, `show_extension`, `dump_repo_mapping`,
  `tidy`.

  **`dump_repo_mapping` is explicitly for us.** `bazel/commands/mod.txt`:
  > "`dump_repo_mapping <canonical_repo_name>...`: Prints the mappings from apparent repo
  > names to canonical repo names for the given repos in NDJSON format. The order of
  > entries within each JSON object is unspecified. **This command is intended for use by
  > tools such as IDEs and Starlark language servers.**"

  This is the sanctioned way to resolve `@rules_go//...` → on-disk path without
  reimplementing MVS. It requires invoking Bazel, so it has the usual cost/lock
  problems, but it exists and is contractual.
- `bazel vendor` (`bazel/commands/VendorCommand.java`, `vendor.txt`): downloads external
  repos into `--vendor_dir`. Adds a **`VENDOR.bazel`** file type
  (`LabelConstants.VENDOR_FILE_NAME`) whose globals are exactly two:
  `ignore(*canonical_repo_names)` and `pin(*canonical_repo_names)`
  (`packages/VendorFileGlobals.java:39,54`).
- **`REPO.bazel`** globals (`packages/RepoFileGlobals.java`): `repo(...)` (package-args
  defaults for the whole repo) and, new in Bazel 9, `ignore_directories(...)` — "takes a
  list of directories to ignore just like `.bazelignore` does, but with `glob`
  semantics".
- 9.0: `--inject_repository` CLI flag; `--override_repository` now accepts **apparent**
  repo names; `single_version_override` to a lower version than a `bazel_dep` is now an
  **error**; external Bzlmod repos may contain a top-level `external` directory;
  user-provided repo names may now **start with a digit**;
  `--experimental_downloader_config` renamed to `--downloader_config`.

### 5.6 Load visibility (`visibility()` in `.bzl`)

`--experimental_bzl_visibility` default `true`.
`starlarkbuildapi/StarlarkBuildApiGlobals.java:31`:
> "Sets the **load visibility** of the .bzl module currently being initialized… The load
> visibility of a module governs whether or not other BUILD and .bzl files may load it.
> (This is distinct from the target visibility of the underlying .bzl source file…)
> `visibility()` may only be called once per .bzl file, and only at the top level, not
> inside a function."

Argument syntax is `package_group`-style specs, **without** negative specs. Governed by
`--check_bzl_visibility` (violations become warnings when false).

**LSP implication**: a *second, independent* visibility system, checked on `load()`
statements rather than on deps. "Can this file load that symbol?" is a distinct
diagnostic from "can this target depend on that target?".

### 5.7 `package_metadata` replaces `applicable_licenses`

`packages/RuleClass.java:149-151`:
```java
public static final String APPLICABLE_METADATA_ATTR = "package_metadata";
public static final String APPLICABLE_METADATA_ATTR_ALT = "applicable_licenses";
```
`PackageArgs.java:186-190`: `package(default_package_metadata = ...)` and
`default_applicable_licenses` are aliases and **cannot both be set**:
> "Can not set both `default_package_metadata` and `default_applicable_licenses`. Move
> all declarations to `default_package_metadata`."

`package_metadata` now appears in the common attribute list on every rule (visible in the
`cc_binary` signature on `bazel.build/reference/be/c-cpp`). The `package_metadata` BCR
module has 46 dependents. Also in 9.0: `--incompatible_no_attr_license` default true;
`distribs` is a no-op; `output_licenses` is now a plain string list.

### 5.8 `select()`, `depset`, `Label`, and other Starlark semantics

- `--incompatible_simplify_unconditional_selects_in_rule_attrs` default **true**
  (a `select()` with only `//conditions:default` collapses to a plain value —
  changes what `bazel query --output=build` prints and what `existing_rules()` returns).
- `--incompatible_resolve_select_keys_eagerly` default **false** at HEAD, listed in the
  9.0 notes (as `--incompatible_eagerly_resolve_select_keys`,
  [#26281](https://github.com/bazelbuild/bazel/issues/26281)) as "will be flipped in a
  future major release". *The flag was renamed between the release notes and the source —
  the notes name no longer exists.*
- `--incompatible_always_check_depset_elements` default true.
- `--incompatible_unambiguous_label_stringification` default true — `str(Label(...))`
  now always yields `@@canonical//pkg:name`.
- `--incompatible_enable_deprecated_label_apis` default **true** (still on): keeps
  `native.repository_name`, `Label.workspace_name`, etc. alive.
- `--incompatible_stop_exporting_build_file_path` default false.
- `--incompatible_fail_on_unknown_attributes` default true.
- `--incompatible_disallow_empty_glob`, `--incompatible_no_implicit_file_export` (true in
  Bazel OSS), `--incompatible_package_group_has_public_syntax` (true, enables
  `//visibility:public` inside `package_group`),
  `--incompatible_fix_package_group_reporoot_syntax` (true).
- `--incompatible_enforce_starlark_utf8` default `"warning"`.
- **`set()` is a real Starlark type** — `--experimental_enable_starlark_set` default
  `true` since 8.x; `net/starlark/java/eval/StarlarkSet.java`. Added in 8.1.0.
- 9.0 removed `None` as an argument to `range()`, `str.split()`/`rsplit()`,
  `list.index()`/`pop()`; `split`/`rsplit` gained keyword args.
- 9.0: legacy `struct` providers gone; string names in `provides =` gone;
  `attr.label_list_dict` added.
- 9.0 symbolic macros: `generator_name`, `generator_function`, `generator_location` **and
  the full Starlark stack** are now set for rule targets instantiated inside a symbolic
  macro. (Directly usable for goto-definition from a generated target back to its macro
  call site.)
- `--experimental_rule_extension_api` default **true** (subrules / rule extension).
- `--experimental_dormant_deps` (false), `--experimental_isolated_extension_usages`
  (false), `--experimental_repository_ctx_execute_wasm` (false — repo rules can run WASM).
- HEAD only: custom Starlark rules named `test_suite` are no longer treated as a
  `test_suite`; `min()`/`max()` key callbacks may not mutate the sequence.

### 5.9 `bzl_library`

Still lives in **`bazel_skylib`** (`bazel_skylib//:bzl_library.bzl`; latest 1.9.2, module
`compatibility_level = 1`), not in Bazel and not in Stardoc. It is a pure
dependency-declaration rule for Stardoc; Bazel core does not know about it. 558 BCR
modules depend on `bazel_skylib` (3rd most-depended-on) and 99 on `stardoc`.

### 7.1 The site was rebuilt three weeks ago

2026-08-05, https://blog.bazel.build/2026/08/05/new-websites-incoming.html: `bazel.build`

`extending/platforms`.

### 7.2 Versioning — and the current release has no docs

`bazel.build/versions/<X.Y.Z>/...` snapshots exist for:
`6.5.0, 7.6.1, 7.7.1, 8.0.1, 8.1.1, 8.2.1, 8.3.1, 8.4.2, 8.5.1, 8.6.0, 8.7.0, 9.0.0, 9.1.0`
(`docs/versions/` in the repo; also probed live).

> ### Known issues:

> — fweikert, [#30598](https://github.com/bazelbuild/bazel/issues/30598), 2026-08-05

Note also that `8.0.0` 404s (only `8.0.1` exists) — the snapshots are per *patch*, not

### 7.3 The unversioned "latest" docs describe **unreleased** behaviour

The version picker offers "Nightly" as a distinct entry, but the *unversioned* URLs are
also built from `bazelbuild/bazel` master — i.e. **Bazel 10.0.0-pre**, not 9.2.0. Proof
by a flag that changed after 9.2.0 shipped:

`--incompatible_modify_execution_info_additive` became a deprecated UNDOCUMENTED no-op in
rolling release `10.0.0-pre.20260729.1` (2026-08-04), *after* 9.2.0 (2026-07-13).

| source | result |
|---|---|
| `docs/versions/9.1.0/reference/command-line-reference.mdx` | ``--[no]incompatible_modify_execution_info_additive`` default `"true"`, fully documented |
| HEAD `BazelRulesModule.java:68` | `documentationCategory = UNDOCUMENTED`, `effectTags = NO_OP`, `help = "Deprecated no-op."` |
| live `https://bazel.build/reference/command-line-reference` | **absent** |

So: the default docs a user lands on describe a Bazel nobody is running, and the docs for
the Bazel they *are* running 404.

### 7.5 New index is incomplete

`https://bazel.build/llms.txt` (the site's own machine-readable index, advertised in a
banner on every page) omits, among others: the **entire `/external/*` tree** (overview,
module, extension, registry, lockfile, vendor, mod-command, migration, repo, faq) and all
of `/extending/*` except `concepts`, and all of `/rules/lib/{toplevel,builtins,providers}/*`.
Every one of those URLs returns 200 when fetched directly. So the index that LLM-based
tooling is being pointed at hides Bzlmod and the extension API.

## 9. Consequences for the language server — condensed

1. **Parse Bazel-9 Starlark, not 2019 Starlark.** Type annotations, `type` aliases,
   `isinstance()`, `cast()`, `...`, `#:` doc comments and `set()` are accepted *today* by
   a default Bazel 9 install. Validate every candidate grammar against them before
   choosing one.
2. **Five-plus file dialects, each with a different global environment.** `BUILD`, `.bzl`
   (BUILD-loaded vs MODULE-loaded vs `@_builtins` — three different predeclared sets, see
   `BzlLoadFunction#getAndDigestPredeclaredEnvironment`), `MODULE.bazel`,
   `*.MODULE.bazel`, `REPO.bazel`, `VENDOR.bazel`, `*.scl` (exactly `{visibility,
   struct}`), `PROJECT.scl`, `WORKSPACE`.
3. **Builtins are version-dependent.** Bazel 7 autoloads ~40 rule names; Bazel 9
   autoloads zero. Key the builtin table on the repo's `.bazelversion`.
4. **Two visibility systems.** Target visibility (now *macro*-scoped, not package-scoped)
   and load visibility (`visibility()` in `.bzl`, `--check_bzl_visibility`).
5. **Canonical repo names use `+`.** `rules_foo+`, `rules_foo+1.2.3`,
   `rules_foo+1.2.3+ext+repo`; main repo canonical name is `""`.
   `bazel mod dump_repo_mapping` is the officially blessed resolution channel —
   the docs say so in as many words: *"intended for use by tools such as IDEs and
   Starlark language servers."*
6. **Symbolic macros are the tractable case and legacy macros are the common case.** The
   naming-prefix rule (`name`, `name_*`, `name-*`, `name.*`) makes target→declaration
   resolution a string operation for symbolic macros; Bazel's own lazy-expansion
   `PackagePiece` machinery is built on exactly that. Legacy `def` macros require
   interpretation and will dominate for years.
7. **Highest-value diagnostic in 2026 is "missing `load()`"**, created by the Bazel 9
   autoload removal, and its fix is mechanical.
8. **Don't trust bazel.build prose.** Generated reference (Java `@StarlarkMethod`
   javadoc → `/rules/lib/**`, `command-line-reference`) is reliable; hand-written pages
   lag 6–18 months and the docs for the current release (9.2.0) do not exist at all.
   Build the hover corpus from `starlark_doc_extract`/Stardoc, or lift it from the
   registry's auto-Stardoc output.
